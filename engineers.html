For engineers

One workflow taken from request to something a team can run: an agent with tools, an eval set, cost and latency on every run, alerts, an MCP server so it works from Claude, a Claude skill, a Databricks notebook for the quality tables, and a handoff runbook.

The AI agent decides

  • Which checks to run, in what order
  • How to read order data that isn't in the documented format (JSON blocks, dataLayer, data attributes, field-by-field assignments)
  • The checklist and the note to the partner's developer

The code decides

  • Every check result, each with an evidence ID
  • The verdict: any blocker means not ready
  • Whether the agent's reading is real: every value it reports must appear on the page

How quality is tracked

Every check is logged with what it decided, how long it took, what it cost, and whether the AI agent had to hand over to the rules. Every change to the prompt or model is run against the example pages first and compared with the last run. If the agent starts failing, or a run catches less than the one before, an alert goes out.

Guardrails

  • A skipped check can't become a "go": if the agent stops early, the rules run instead
  • Values the agent reads must appear on the page, or the data is marked "could not confirm"
  • Problems the agent names that no check found are logged as unbacked and kept out of the verdict
  • Page text is data, never instructions; one example page tries prompt injection and is in the eval
  • Rate limits per visitor and per day; the agent eval needs an access code

Use it from Claude

  • MCP server with three tools: list_example_pages, check_partner_page, quality_report
  • A Claude skill, partner-go-live-review, that tells Claude how to run a check and answer a partner manager in plain words
  • Works in Claude Desktop and Claude Code with one config entry

What it doesn't do yet

  • Pages that build order data with JavaScript after load need a headless browser
  • Real pages need a test order, and two for the order-ID check
  • The spec is an example from public post-purchase integration guides, not the network's real tag
  • Partner IDs should come from the partner record (CRM), not be typed in

Tests

  • Tests against real Redis and SQLite
  • Scripted-model tests: a model that invents clean values, obeys an injected note, or skips checks still can't pass a broken page
  • SSRF refusals, path traversal into the app, alerts on eval regressions, run logging

Handoff

The runbook names a business owner, the before/after number Finance would sign off on (time from "integration done" to "live"), what healthy looks like for each signal, how to change the prompt or model safely (rerun the eval, ship only if it's the same or better), and how to turn the agent off.
